# Laya Decision Models — specialised judges instead of LLM calls

> **Program retired 2026-10-21 — hosted TypeSafe Jev replaced Laya for both live slots.** Jev (api.typesafe.ai `POST /v1/systemone`, same noul/choice/score primitives, no fine-tuning, $0.042/Mtok input, output free, ~185 ms p50 per call, key `TYPESAFE_API_KEY` in the Hermes dotenv, pin `jev-1.14.0` — `jev-latest` moves) scored zero-shot AUC 0.796 / cvR 0.447 @ P≥0.95 on the 359-row gold pool vs trained plain ModernBERT 0.861 / 0.715 and Laya G 0.863 / 0.673: less accurate than a fine-tune, but ~2/3 of its recall for zero labels, training or hosting — and the trained gates never shipped. Live, all env-gated in the gateway drop-ins: store gate (`STORE_GATE=on`, `STORE_GATE_BACKEND=jev`, drop at p_drop ≥ 0.70), supersede judge (`SUPERSEDE_JUDGE=true`, pairwise over the cos 0.80–0.92 neighbour), distill selector (`DISTILL_JUDGE=true`). The reranker stays the local bge cross-encoder: `RERANK_BACKEND=jev` exists as a switch but lost the pre-registered ship rule (KB set +0.040 MRR, reference set −0.024, both CIs spanning zero), and a local reranker keeps the hosted judge independent for retrieval eval (`eval_recall.py --judge`). Every question and threshold lives in `scripts/knowledge/jev.py` — edit the policy there, never in a caller or a JSON under `cache/`. `JEV_WITHHOLD` (default on in code) is the regex privacy switch that keeps work-tenant text off the vendor; the user may turn it off per environment. Jev's only accuracy lever is question/criteria text, and tuning it on the gold pool is post-hoc — confirm on a fresh set. Integration procedure, framing rules, rollback/replay and test pitfalls: `references/hosted-judge-integration.md`. Benchmark harness: `cache/laya-exp/jev/run_storegate.py` → `cvdev.py`. The procedure below (labels, sealed test, attribution, predictions-first) still applies to any judge, Jev included.

The pattern from arXiv:2503.23303 (SalesRLAgent, same author as Laya): take a yes/no, choice, or score decision that an LLM currently makes per call, and move it to a small trained predictor over embeddings that answers in ~30–100 ms on CPU with a calibrated confidence and an explicit "don't know". This skill covers the Laya sandbox harness on this host, the settings that matter, and the benchmark-or-kill protocol. It does NOT cover retrieval itself (embeddings, rerankers) — Laya never finds documents, it judges them. Sandbox is a uv venv; nothing is wired into the live pipeline.

## When to Use

- "Can Laya / a small classifier gate X?" (memory writes, rerank relevance, skill routing). The procedure (labels, sealed test, in-distribution calib, attribution test) applies to ANY small classifier. For a single-text yes/no, the measured winner was a plain ModernBERT fine-tune, not Laya (see Pitfalls)
- A per-turn LLM judgment is too slow or too expensive and has gradeable labels
- "Is this fact worth storing", "should this skill load", "does this passage answer the query"
- Reading or citing the SalesRLAgent paper → load `references/salesrlagent-paper.md`

## Choosing the slot before the experiment

When the user asks where a small model belongs in the RAG pipeline (reranker? filter? metadata?), decide the slot from the competitor and the bar, not from the model's branding:

- **Reranker slot** competes with bge-reranker-v2-m3 (trained on millions of pairs) on MRR AND on the live per-query latency bar. A ~2k-synthetic-pair cross-encoder almost never clears both — state P(ship) ≤ 0.15 up front and run it only as a bounded experiment with the bar pre-written. A hosted zero-shot judge is a different case: with fan-out (one request, one noul per candidate) Jev scored the whole 30-row pool in ~0.25 s — faster than bge — so do not reject that arm on the "per-pair latency" prior; run the four-arm harness in `retrieval-benchmarking` (§ Swapping the reranker) on EVERY query set you have before flipping. Measured here: KB set +0.040 MRR (CI spans 0), reference set −0.024 (8 wins / 15 losses) — speed real, quality a wash, so bge stayed. Read every finished result file (`ls -lt` the results dir) before acting on a ship rule: a compaction summary's "not yet run" is a claim about the past, and the flip made on half the evidence had to be reverted. Beyond accuracy, a hosted reranker puts a vendor on the per-turn path and makes the local one an untested fallback; keeping the local reranker also keeps the hosted judge independent as an eval scorer. Kaggle kernel rules for this arm (each cost a re-run): size the wall clock first — `epochs × epoch-time × kernels ÷ 2 GPU slots` (ModernBERT-large, batch 8, max_len 512 ≈ 75 min/epoch on a T4); if dev AUC saturates after epoch 1 (≥0.98 on synthetic pairs) train ONE epoch rather than three. Before re-pushing an errored kernel, pull its log (`kaggle kernels output <slug> -p <dir>`) and read the last progress line plus the exception — the two arms died of different OOMs: the Laya arm held the whole checkpoint on the GPU through the `state_dict()` views kept in the encoder dict (copy them `.detach().cpu()` and `del` the dict after `load_state_dict`; a second `from_pretrained` for a weights-diff check is CPU-side and harmless), and the vanilla arm died at the first backward of epoch 2 because the larger eval batches left the allocator fragmented (`torch.cuda.empty_cache()` after eval, `expandable_segments:True`). Save a checkpoint after every epoch so an OOM never erases a finished one. Wrap every `kaggle kernels output` download in `subprocess.run(..., timeout=900)` with one retry: a 1.5 GB weights download hung for 4 h (0-byte `.pt`) and stalled the whole runner behind it; the runner should score what downloaded and mark the rest missing, never block. Parse `KernelWorkerStatus.ERROR` with a dotted-token regex (`"([\w.]+)"`), or the monitor spins forever on an errored kernel.
- **Write-time filter slot** (heartbeat/memory ingest) has no latency bar and competes with a regex and a centroid — that is where an encoder classifier earns its keep. Narrow the label to something two humans agree on ("instruction/code/narration stored as a fact" vs "declarative fact"), not keep/drop: the broad gate's ceiling was label noise (κ≈0.57, oracle 0.74), and dupes/superseded rows are FACTS for a leak filter, never positives. Measured twice on this store (store-gate 0.67, leak-gate 0.71 recall at the P≥0.95/FPR≤3% operating point vs a 0.80 bar): shape classifiers plateau at ~0.7 regardless of backbone, and the Laya checkpoint hurt again (−0.07, CI crossing 0). **Before a third shape-classifier on this store, ask whether the signal is available at write time as metadata instead** — who wrote the row (`source`, a `prov:<label>` tag, caller identity) separates agent-extracted from user-stated text exactly, with zero model and zero latency; the classifier was guessing provenance from shape. Prefer stamping provenance in the writers and a read-side marker/supersede guard over any further leak-gate training. The two kills together are the exit criterion: stop single-text gates on this store.
- **Query-time hard filter by metadata** (sector) loses: on a few-hundred-row store ANN over everything is already fast, and every misclassification becomes a hard recall loss; the soft boost dominates (measured P@5 1.0). Backfill metadata if you like, never gate on it.
- **Supersession** is pairwise (does B contradict A) — cross-encoder-shaped, and needs labelled pairs you probably do not have yet; say so instead of forcing it into a single-row gate. Pairs now accumulate as a by-product (2026-10-21): `knowledge_db/deleted_facts.jsonl` holds every deleted row — kNN dedup writes `reason=superseded-by:<new_id>`, the `memory_remove` tool writes `reason=memory_remove` (plugin `_remove`, no replacement id — pair it at label time), and hand-recorded closures go in `cache/laya-exp/data/supersede_pairs.manual.jsonl`. Run `cache/laya-exp/mine_supersede_pairs.py` (needs SUPABASE_URL/KEY in env) to build `data/supersede_pairs.jsonl` and read the count against the 150/class bar. Expect most knn-dedup positives to be restated digests, not state changes — the manual closures are the informative ones. Negatives (same topic, both still true) are mined at label time from near-neighbour pairs (cos 0.80–0.92). Do not train before the bar; below it, the regex status marker + writer discipline carry staleness.

- **Digest-item selector slot** (`session_distill.py`): the extractor over-collects (bare status words, the agent's own instruction text, narration, fragments — roughly half of ~400 sampled Decision/Outcome/Directive items) and then caps each section with `sorted()[:N]`, i.e. alphabetically, so what survives into the digest is a function of leading punctuation. Prefetch injects `text[:250]`, so a digest's visible excerpt is mostly that noise. The judge shape is selection, not gating: one fan-out request per digest (state = title + opener, one noul per item), drop below threshold, then rank the survivors by probability for the cap. Measure first: blind-label ~40 items before scoring so the judge is graded, not anchored; the 3-line regex alternative (order-of-appearance cap + longer bare-word list) recovers the sort bug but cannot separate narration from a decision.

Free labels for the filter slot already exist: every cleanup pass's deletion backups (`~/backups/knowledge-store/*.json`) are leak positives once dupes/digests are excluded; the live kept rows are negatives; rows the orchestrator rescued from a candidate list are the hard negatives. Seal the test by TIME — the whole most recent cleanup pass is TEST, earlier passes train — because that is exactly what "catch the next pass" means. Use the base-size backbone (~150 positives overfit large) and keep a TF-IDF+LR arm that ships if it ties.

## How to Run

Invoke the harness through the `terminal` tool from the sandbox dir:

```
cd ~/.hermes/cache/laya-exp && OMP_NUM_THREADS=8 HF_HUB_OFFLINE=1 \
  venv/bin/python laya_judge.py --in data/expA.jsonl --out results/A_zs_english.jsonl \
  --model english --question-file q_store_gate.json --batch-size 8 --max-len 512
```

Input rows `{"id", "state"}`; output rows `{"id", "answers": {q: {answer, confidence, distribution}}, "latency_ms"}`. Grade with `execute_code` against the `label` field of the matching data file.

## Procedure

1. State predictions and the kill rule BEFORE running (Andrew audits metric changes): expected F1/precision, the baseline it must beat, Δ < bootstrap CI = noise = kill. Write them to a dated `PREDICTIONS-*.md` file before any job reports, with a confidence per claim and a "what would change my mind" list.
2. Build the labeled set read-only from live data (Supabase SELECTs, `state.db` opened `mode=ro`); split by session/query, never by row. Dedupe identical texts first, then write the split INTO the data file (`split` field) so every job (Laya, SetFit, loop) evaluates on the same frozen test rows — never let a child make its own split. Thresholds and temperatures come from the calib slice only.
3. Spot-check the labels yourself before any training (20 rows) and look for structure, not just errors: a source prefix, a template, a field that predicts the label. Compute the cheapest trivial rule that exploits it (e.g. `text.startswith('Session:')` → drop) as a baseline alongside the live one (regex, reranker threshold sweep, keyword scorer) into `data/baseline*.json`. Report every model on the full test set AND on the hard subset the rule cannot reach — that subset is where a model has to earn its keep.
3b. Measure label consistency with a second labeler (`judgeloop agree --labeler qwen|human`, Cohen's κ). A same-model spot-check is not independent. κ < 0.6 caps any model's achievable score; say so before blaming the model. For a live-verified test set, re-verify a random ~60 rows with a second blind verifier subagent, adjudicate each disagreement yourself from the two evidence lines, and freeze the result as a new test version (`test_v2.json`, changes listed) that every later retrain is scored on — re-score earlier runs on it too so comparisons stay like-for-like. Disagreements concentrate on borderline keeps (bare config lines, the employer's end-user support cases); expect ~88% raw agreement between careful verifiers.
3c. Test labels must not come from the teacher that labels training data — grading the student against its own teacher measures agreement, not correctness. If the user asks the agent to fill the test worksheet, say why that defeats it and offer, in order: blind human labels on the hard subset only (~50 rows); a pre-filled sheet the user skims and flips (fast, but anchored); live-evidence verification. For the last, fan out ~30 rows per subagent, read-only: each row gets a verdict CURRENT / STALE (cite the replacement) / PARTIAL / UNVERIFIABLE / NOT_A_FACT, a keep/drop label, a one-line evidence citation, and a changed-vs-prefill flag (the flip rate estimates the original label noise). Never test credentials found in rows.
4. Zero-shot pass with `noul` questions, English checkpoint, `--max-len 512`. Expect near-chance (repo's own benchmark: base checkpoints ≈ random on novel yes/no tasks). This is the control, not the result.
5. Fine-tune only if labels ≥ ~150/class. WHERE: off-box first — Kaggle free 2×T4 via the CLI (recipe: `references/off-box-training.md`). Andrew's standing rule: training must not touch anything that serves the live agent unless there is no alternative; LH02's Ollama embeddings/reranker back every per-turn memory lookup, so LH02 MPS is the fallback, and LH01 CPU is never used for a real fine-tune. Order (any host): `laya-train --help` (never invent flags) → `--dry-run` → positive control (trivially separable set; ~26 s on MPS, must hit ~100%) → real run (`--base english --loss soft-ce --eval calib.jsonl`, ~8 epochs, seeds 0/1/2). Launch each run DETACHED: `ssh localadmin@<LH02-tailnet-ip> 'cd ~/laya-ft && nohup ./run_s0.sh > logs/s0.log 2>&1 < /dev/null &'`, then poll the log with short ssh calls — a held-open ssh dies with the orchestrator. Keep `PYTORCH_MPS_HIGH_WATERMARK_RATIO=0.5` and curl Ollama `/api/tags` after each run (shared host). Also score the BASE checkpoint on the same test rows so zero-shot vs fine-tuned is like-for-like. Gate on `answer_confidence`, not `confidence`.
5b. After export, open the checkpoint config: if it still carries the base model's `temperature_by_options` (English noul:2 = 1.9834), those inherited bucket values override the newly fitted per-type `temperature` at inference. Report ECE as-exported AND with the key removed (on a copy). AUC and calib-chosen-threshold F1 are unaffected; confidence cutoffs and coverage@P are not.
6. Attribution test: prove it is LAYA doing the work, not the labels and the eval hygiene (those help any classifier). Write the arms and the decision rule into `attribution/PREDICTIONS.md` before launch. Then run them on Kaggle with the identical train/calib/test data and the identical calib-transfer threshold rule:
   - (0) Laya trained on SHUFFLED targets. It must land at AUC ≈ 0.5; anything higher means the pipeline leaks.
   - (1) TF-IDF word+char n-grams + logistic regression.
   - (2) Frozen small embedder (bge-small) + LR.
   - (3) SetFit (bge-small or all-mpnet-base-v2, `batch_size ≤ 16`, `num_iterations ≤ 10`; hard labels only).
   - (4) The same backbone (ModernBERT-large) fine-tuned with plain HF Trainer and soft-target CE, no Laya code. This isolates the framework from the backbone.
   Run a paired bootstrap of ΔAUC and Δrecall vs EVERY arm. Laya wins only if each CI lower bound is > 0; otherwise ship the cheapest arm inside the CI. Record train time and CPU ms/row per arm. For relevance tasks, the rival is the existing reranker threshold sweep.
   - Have every rival arm `save_pretrained` its weights (or pickle the sklearn model) as kernel output. If a rival wins, it ships; without saved weights you pay a Kaggle re-run before you can even measure deployment latency.
   - The shuffled-label arm only proves Laya's pipeline is leak-free. A rival that beats Laya runs separate code, so audit it before trusting the win: quote the kernel lines that select training rows (`split == 'train'` only; calib/test used for inference only, never for early stopping or model selection), and confirm max_len, lr, epochs and effective batch match Laya's config. Put the audit at the top of RESULTS.md.
   - Validate the scorer against one known number first (e.g. a Laya seed's AUC from the earlier run) so rival and Laya scores come from the same code path.
   - When a rival wins and the user still wants Laya trained ("keep training"), do a catch-up retrain, not another blind seed sweep. First write `CONFIG_DIFF.md`: every EFFECTIVE difference vs the winning arm, cited file:line from the laya source + run config (internal calib holdout, exact input string and its token overhead, encoder/head lrs, warmup/scheduler, pooling, head, loss details, clipping, precision, freezing, checkpoint selection). Then run cumulative arms, each removing one gap (A: no internal holdout / external calib; B: + minimal framing; C: + matched optimizer/schedule, documented kernel monkeypatch allowed), 3 seeds each, scored with the same paired bootstrap vs the winner. The ship rule stays unchanged: the winner ships unless a Laya arm matches it on AUC AND on recall at P ≥ 0.95. A tie means the gap was configuration, not the framework.
   - If every catch-up arm still loses, the gap lives in what Laya cannot drop: its head (a 2-layer TransformerEncoder, ~17M params, vs CLS→Linear) and its STARTING WEIGHTS (`convaiinnovations/laya` is its own pretrained checkpoint, not vanilla ModernBERT-large). Check which backbone weights each arm actually loads before calling any comparison "same backbone". Stop blind retrains at that point; they cannot close an architectural gap. If the user still says "keep training", the one Laya retrain worth running is the starting-weights diagnostic, with everything else the same as the best catch-up arm and 3 seeds per arm, one kernel per arm:
     - V1 = vanilla encoder + Laya's PRETRAINED head (isolates the checkpoint).
     - V2 = vanilla encoder + RANDOM head (framework only, no Laya weights).
     Build the hybrid start checkpoint in-kernel with laya's own load/build/save functions (recipe: `references/off-box-training.md` §5d). Pre-register the outcomes: V1/V2 tie the winner → the checkpoint was the handicap and Laya-on-vanilla becomes Laya's best config (ship rule unchanged). Both ≈ the earlier Laya arms → the head/framework is the cause, so stop Laya on that single-text gate and move it to a structured/pairwise gate. V2 > V1 beyond the CI → the pretrained head hurts. A V2 collapse (a seed near chance) means the random head was under-trained at that update count, not that the framework failed; re-run it with more epochs before concluding. Tell the user up front that this is a diagnostic, not a path to beating the winner.
     - Measured (store gate): the CHECKPOINT was the whole AUC gap. Vanilla weights reached ens AUC 0.899 (V1) / 0.902 (V2) vs plain 0.892 (tie) and vs the Laya-checkpoint arm 0.825 (+0.074, CI [+0.03, +0.13]); the head is neutral (V2 − V1 +0.003, CI spans 0). Default to vanilla ModernBERT-large weights for any new Laya fine-tune.
     - Measured (store gate, pooled 359-row CV recall @ P ≥ 0.95): on-distribution GOLD rows are the lever that moves recall. A 5-fold gold cross-fit (train on teacher rows + the out-of-fold verified rows, predict the held-out fold) went from 0.605 to 0.673. Dropping the 483 tied soft labels did nothing (0.588). Relabelling ties + new rows with the "best" LLM labeller HURT (0.577 alone, 0.615 with gold).
     - A labeller bake-off on a class-balanced gold set can't see base-rate bias. The winner (VF on Sonnet) was the existing VF baseline, so "tie-breaking" just sided with a keep-biased labeller: 46% keep on new rows vs 21% in the target pool. Judge labellers on a set whose class mix matches the target, and compare their predicted keep-rate to the target base rate before relabelling anything.
     - An AUC tie is not a ship. The vanilla arms still lost calib-transfer recall (0.49 vs 0.71 at P ≥ 0.95, CI [−0.30, −0.14]) because they ranked the 209-row calib set worse (AUC 0.80 vs 0.84) while ranking the test set better (oracle cov@P95 0.86 vs 0.75). When AUC ties but operating-point recall diverges like this, switch to the pooled-CV metric (step 6b) before deciding anything. On the pool the "tie" disappeared: Laya-vanilla AUC 0.849 / cvR 0.605 vs plain 0.861 / 0.715.
   - When explaining a loss, state the mechanism: Laya is NOT the same backbone with extras. It starts from different pretrained weights and adds framing, a transformer head, per-question heads and temperature fitting. Temperature scaling is monotone (AUC unchanged). Measured: removing the calib holdout (+262 rows), the framing, and matching optimizer/schedule/weight decay each moved nothing or hurt (ens AUC 0.825 / 0.789 / 0.808 vs plain 0.892); the question framing helps Laya, so keep it. It is not a "superior version" of the backbone.
6b. Pooled-CV operating point, for when the calib and test sets are each only ~150–200 rows and disagree. Recall at a calib-picked threshold then swings by ±0.2 on sampling alone, because the P ≥ 0.95 cutoff lives in the top ~10 keeps.
   - Pool every live-verified row (calib + test), with test labels taken from the adjudicated `test_v2.json`, not from the dataset's label field.
   - Score with repeated stratified K-fold threshold transfer (`cvdev.py` in the sandbox: 5 folds × 20 repeats; the threshold is the lowest score with precision ≥ 0.95 over ≥ 10 picks on the other folds; recall and precision are pooled over the held-out folds).
   - Report pooled AUC, cvR with its repeat range, and oracle cov@P95 for every arm, including old arms re-scored from their saved predictions. Treat Delta cvR < ~0.04 as noise.
   - Disclose that the sealed test is now inside the pool, and require a NEW fresh set for any final ship claim.
   - To train on that gold without leaking it, cross-fit: for fold k, train on the train rows plus the pool rows outside fold k, and predict only fold k. Each pool row then gets exactly one out-of-fold prediction per seed. Verify that count before scoring.
6c. Error analysis before choosing the next lever. Print the label string in model-rank order (D/K) and the text of every keep ranked inside the would-be operating region. If several of those keeps look like gold mistakes, eval-label noise caps recall. Fix it only by blind re-verification of ALL (or randomly sampled) eval rows plus adjudication of the disagreements. Never relabel the rows the model ranks high: correcting only model-selected rows biases the metric toward the model.
7. Report a coverage curve, not only F1: precision at 10/20/30/50% auto-coverage and the max coverage at precision ≥ 0.95. A gate that only acts on its most confident slice can be useful when it fails at deciding everything. The loop's promote bar is F1 ≥ bar OR coverage@P0.95 ≥ 0.20, and it must beat rule + current model by more than the CI.
7a. When the user asks how to prove the model is doing the work, the answer is step 6's attribution test: launch it in the same turn, and explain it as same data + same test + same threshold rule, with Laya required to beat every rival by more than the paired-bootstrap CI.
7b. Export before any shadow run, on Kaggle (attach the training kernel's output; TorchScript path `dynamo=False`, `external_data=False`). Run a parity check on calib+test (mean |Δp| vs torch, test AUC) for EVERY exported variant before using it. Dynamic INT8 on the 421M ModernBERT-large checkpoint collapses even with `per_channel=False` (mean |Δp| ≈ 0.25, AUC 0.82 → 0.55–0.67) and was no faster than fp32 on this host's CPU (p50 ~170 ms both). Ship fp32 (exact parity, ~1.7 GB per seed). Measure p50/p95 per fact yourself, inside the capped scope, with `intra_op_num_threads=1`: one fp32 seed ran at p95 ≈ 257 ms under `nice 19`, 1 core, 3 GB.
7c. Offline shadow over the live KB: score read-only, then blind live review. Take the top-50 flags plus 50 random unflagged, shuffled, with no scores in the reviewers' key file; ~25 rows per verifier subagent. Then split the flagged rows by whether the trivial rule (e.g. `Session:` prefix) already catches them. On this KB, 42 of the top 50 flags were rule-caught, so 49/50 agreement mostly measured the rule. The gate's value is precision and volume on the NON-rule rows: score those separately and live-verify ~50 of their flags before calling the shadow bar passed. Random unflagged junk that is STALE belongs to the supersede gate, not to this one.
8. Wiring comes only AFTER the usable bar passes — never while the model is still training (the model keeps changing under the hook, and a half-trained gate in the save path silently loses good facts). Default order once the bar passes: written proposal (hook point, effect, rollback) → **implement directly, env-gated, with the rollback written before the flip** — the user does not want log-only shadow weeks ("forget the shadow stuff, implement right away, set up a rollback plan"); a shadow is only for a model that is still changing. Rollback has two halves and both are required: behaviour (one `Environment=` line per judge in a systemd drop-in; remove + daemon-reload + restart) and data (every drop/delete logged with the FULL text so a replay script can re-store it — `scripts/jev_restore.py` is the shape). Auto-act only at the pre-registered P ≥ 0.95 operating point; abstention/vendor failure falls back to today's behaviour. Record the verdict in `retrieval-benchmarking`.
   - Live shadow shape that shipped for the store gate: `scripts/knowledge/store_gate.py` (`score(texts) -> p_drop`, lazy single load, CPU, `torch.set_num_threads(4)`, threshold constant from the sealed calib) hooked into `session_heartbeat.process_session()` only when `STORE_GATE=log`; env lives in a gateway drop-in (`~/.config/systemd/user/hermes-gateway.service.d/store-gate.conf`) because the heartbeat runs inside the gateway — a restart is what turns it on, confirm with `/proc/<MainPID>/environ`. Weights live under `~/.hermes/models/` (gitignored), never under `cache/` where a prune can take them. Smoke the deployed checkpoint with one obvious drop and one obvious keep BEFORE wiring: a reversed order means the label index is flipped, and the only symptom in shadow would be a week of inverted verdicts.
   - Every shadow line records `verdict`, `stored`, and `guard_rejected` (did the existing rule/guard already reject it). Keep the existing heuristics and dedup running through the shadow week: dedup is a different job the classifier never learned, and the guard-overlap column is the decision input — the review question is "how much does the model catch BEYOND the guard, at what precision", pre-registered as flag-precision ≥ 0.95 AND ≥ 50% of what the guard lets through; archive the guard only when the model's drop set covers ≥ 90% of the guard's rejects. Pulling the heuristics first destroys the comparison and lets a week of unfiltered extractor output into the store.
   - Reviewing a gate that "failed its bar": a 0.80 recall bar below a 0.742 oracle ceiling is unreachable by any model; recall ≈ 95% of the ceiling at P ≥ 0.95 is a shippable auto-act-only gate, not a failure. Say both numbers when proposing it.

## Long autonomous programs

When granted autonomy to "train until optimal and usable", first write the program file `~/.hermes/references/laya-program.md` (host path, outside this skill): mandate, scope boundary (autonomy = data/labels/training/eval/export/offline shadow; live wiring is still proposed), phases, and a decision log. Fix the usable bar in it BEFORE results: the mean of 3 seeds passes the paired bootstrap vs the rule on a fresh live-verified test set (≥ 150 rows never used for model or threshold selection); precision ≥ 0.95 at ≥ 20% coverage OR F1 ≥ 0.85; hard-subset AUC ≥ 0.80; calibration fitted on ≥ 200 rows and not at the temperature clamp; LH01 CPU p95 ≤ 300 ms; offline-shadow top-50 agreement ≥ 90%. "Optimal" = more data/budget no longer moves those numbers beyond the CI.

Before scoring anything on a NEW test set, compute every baseline on it first: the rule, all-drop, and the teacher's own labels. If the rule never fires there (e.g. no `Session:` rows) or all-drop already clears the F1 bar (drop-heavy set: 75% drop gives F1 0.86), those bars are meaningless on that set. Replace them BEFORE any model result exists and say so in the predictions file: primary = recall of drops at a calib-picked P≥0.95 threshold applied to test (mean of 3 seeds), plus threshold-free AUC, with the teacher's per-row LLM call as the reference operating point (matching it = a free local replacement for a paid call). Seal the fresh test ids in a file, exclude them from every training and teacher-tuning set, and score each retrain on them exactly once. Write a `PREDICTIONS-<experiment>.md` before each run. Check plan utilization before every fan-out; pause new fan-outs at ~65% so the 75% ceiling keeps headroom for the live agent. The cheapest live gauge is the last line of `teacher/usage.log` (`5h=… 7d=…`) while the teacher unit runs. Kaggle training costs no Claude quota, but a subagent that has to re-read the program context does. Near the pause threshold, write and push small kernels inline (template: copy the latest kernel and change only the arm), and keep subagents for the work that needs reasoning.

When the user sets a numeric target without naming the metric ("get it to around 0.8"), pick the metric the gate is currently losing on (usually recall at P ≥ 0.95, not an AUC it already clears). Say the reading in one line of the first reply, write it at the top of the program's PLAN file with the baselines on that metric, and proceed without blocking. The user corrects it if wrong. Also give an honest P(reaching it), anchored on the best model's oracle ceiling at current label quality.

Resuming ("where were we"): run `memory_search` for the gate, then read `laya-program.md`. Its Log section is newest-first, so the top entry is the current state. Then run `ls -lt` on the sandbox to catch any run newer than the log. Answer briefly: the verdict and standing numbers, whether anything is running (only with a live handle), the open next steps, and one recommendation. Every launch or decision gets a log entry at the TOP of the Log section (time, arms, kernel refs, predictions file, usage gauges), backed up first.

Plateau diagnostic — run it before buying more epochs, rows or seeds:
- When two retrains that change budget/volume land within seed noise, score the TEACHER's labels on the same sealed test (balanced accuracy, per-class precision) and the live verifier's accuracy (from the inter-annotator check). Student ≈ teacher means labels are binding; the gap between student and verifier is the room left, and only a better labeller closes it.
- Inspect the soft-label VALUE distribution, not just the mean. A vote-mean of two labellers yields only {0, 0.5, 1}. Every 0.5 is a tie that carries almost no gradient (here 483 of 2,375 teacher rows, 20%). Rows the teacher never relabelled with the current rubric are a second free pool. The targeted fix is a third labeller that breaks only the ties and labels the unrelabelled rows. Select it on gold that sits in TRAIN only (e.g. the hand-labelled rows), never on calib/test, and require a balanced-accuracy floor (≥ 0.80) before it touches the data.
- Then run a label bake-off (`references/teacher-labeling.md` §7) instead of another retrain, and write the stop rule into the next PREDICTIONS file before launch: below the floor (here mean test AUC < 0.79) stop iterating that gate, ship the best ensemble at its calib-transfer P ≥ 0.95 operating point as an auto-act-only gate (abstain = today's behaviour), and move effort to the next task (e.g. the pairwise supersede gate).
- Any post-hoc choice made on the bake-off dev set (e.g. combining two labellers) is disclosed as post-hoc in the predictions file; the sealed test, not dev, decides.

Progress updates and ETAs:
- When a reply commits to starting something ("I'll start the comparison now"), make the launching call in that same turn; a promise in prose is not a launch.
- Call a workstream "running" only when it has a live handle: a unit that is active, a Kaggle kernel ref, or a returned subagent id. Saying "I'll start X" and then reporting X as running without the call having returned is a false status. If an update over-claimed, correct it in the next message.
- Report each slot with one of three words and nothing softer: **implemented** = code in a live path and the first log row seen; **piloted** = a script ran on sample rows, nothing calls it; **decided** = a memory/log entry exists. "Replace Laya for slots 1 and 2" followed by a pilot script for slot 1 is a decision plus a pilot, and the user will ask "so what's actually implemented?" — answer that question in the report before it is asked, and count a shadow as unconfirmed until its first `backend`-tagged line lands.
- Results that land after the turn ends (Kaggle kernels, ~30 min/arm) need a trigger to get scored: the user's next message, a one-shot cron, or — preferred for multi-hour runs — a detached `systemd-run --user --unit=<exp>-run<N> --collect -p MemoryMax=6G /bin/bash launch.sh` whose script runs push→monitor→download→score→RESULTS.md and then posts the verdict section to the user's chat through the Telegram bot API (`TELEGRAM_BOT_TOKEN` read from `~/.hermes/.env`, chat id from the session context; `sendMessage` via urllib, no deps). The unit survives gateway restarts; a `delegate_task` child does not. Say which trigger applies. Don't promise to "report back" when nothing will wake you, and never park a background sleep/poll loop.
- For kernel status, read the slug from each kernel's `kernel-metadata.json` (`id`), never reconstruct it from the run name. A guessed slug returns the same "Permission 'kernels.get' was denied" as a private kernel, which looks like an auth failure.
- Verify a child's "done" against its artifacts before you report it: open the output files, count rows, and diff arms that should differ. Children report a step as run when a silent fallback produced a copy of another arm's output.
- Answer "what's the ETA" from one batched read of live state, not from the last estimate: teacher labels so far plus label rate, checkpoint position vs the total pool (recipe: `references/teacher-labeling.md` §3), pending kernel/subagent results, and the 5h/7d gauges. Then give a timeline with clock times for each gate (budget results → label QC → backlog done → fresh test + calib sets → 3-seed retrain → scored vs bar), the headline time first, and name what could push it back (label QC flip rate > 10% adds a relabel pass, Kaggle queue, usage).

## Pitfalls

- Before delegating an experiment, do the gated steps yourself: create the venv and `uv pip install` its packages, and pre-resolve any version pins (smoke-import the top-level package). A subagent cannot answer the write-gate's approve prompt; a correct one stalls at the install and returns "BLOCKED" after burning its context on prep, and a wrong one routes around the gate. Hand it an already-importable environment plus the PLAN.md.
- Give every child that loads models (export checks, latency benches, KB shadow scoring) the scope command verbatim, and tell it to score one seed at a time. A child that runs shadow scoring under `nice` alone loads 3 × 1.7 GB fp32 seeds uncapped next to the live gateway.
- Run every model-loading process on LH01 inside a capped transient scope: `systemd-run --user --scope -q -p MemoryMax=8G -p MemorySwapMax=0 env OMP_NUM_THREADS=4 TOKENIZERS_PARALLELISM=false HF_HUB_OFFLINE=1 <venv python> …`, one at a time. An uncapped SetFit run grew to ~19 GB, the kernel OOM-killed inside the gateway's cgroup, and the gateway went down with every running delegate child. Remote training launches `nohup … &` on the remote host, never a held-open ssh.
- When the user asks how to speed up training, answer with data, not compute: at a few hundred rows a Kaggle seed takes ~3 min, so the wait is labelled rows. Levers, biggest first: teacher concurrency (2–3 requests in flight while 5h usage is low: same tokens, a fraction of the wall time) → cheaper model for the extraction step, strong model only for labelling → free labels already on disk (cleanup-job deletions, `[SUPERSEDED …]` rows, pending-memory review outcomes) → run the label-quality check early instead of after the backlog → build the fresh test and calib sets in parallel. Count the real candidate pool and pilot before quoting volume or cost: `references/teacher-labeling.md`. Per-run knobs (`max_len 256`, `--freeze-encoder`, multilingual checkpoint) are for iteration speed, not accuracy.
- Keep the default `TrainConfig` (micro_batch=8 × grad_accum=8). At 185 rows that is only ~24 optimizer updates, but grad_accum=1 (8× the updates) moved nothing (AUC 0.836 vs 0.84, same seed spread), so the update count was not the constraint. The default scales on its own: ~2k rows × 4 epochs ≈ 140 updates. Look at labels and the calib set size before touching the budget.
- The calib set decides whether thresholds transfer. With 16 calib rows, re-picking the threshold by an equally valid rule flipped kill-rule verdicts both ways, and the noul temperature sat at the `TEMP_MAX=5.0` clamp (common.py:836). With 210 live-verified calib rows, the calib-picked P≥0.95 threshold held on the sealed test (test P 0.95–1.00) and soft-CE temperatures came off the clamp (3.2–4.2). Make calib ≥ 200 live-verified rows before any confidence-cutoff claim. Size is not enough: calib must come from the SAME distribution as the test/deployment rows. Reusing older verified rows (expA-style `Session:` summaries and memory facts) as calib for a teacher-row test made calib precision run ~7 pts below test at the same threshold. The P≥0.95 rule then picked far-too-strict cutoffs: calib-transfer drop recall 0.26–0.34 against an oracle 0.65, and one seed had no threshold at all. Draw calib by the same sampler as the test (e.g. a live-verified dev set), and move the old verified rows into train as gold. Doing exactly that fixed transfer with no other change: every seed got a threshold, test precision was 0.95–1.00, and recall rose from 0.26–0.34 to 0.39–0.61 (ensemble P 0.98, R 0.51).
- Averaging the p_drop of the 3 seeds is a gain at the operating point (coverage at calib-picked P≥0.95: per-seed 0.30–0.33, averaged 0.35), but it costs 3× latency and 3× memory. The one-seed limit is a HOST constraint, not a model one: fp32 ~1.7 GB per seed does not fit a 3 GB co-hosted cap on the Mini, but on LH02 (MPS fp32, batch 1: p95 ~17–25 ms idle, ~28–37 ms while Ollama generates) a 3-seed ensemble fits easily, so re-decide ensemble vs single seed whenever the target host changes. When one seed must ship, pick it by CALIB AUC, never by test score, so the sealed test stays unspent. Report the ensemble next to the per-seed mean, never instead of it.
- Compare like with like: ensemble vs ensemble, single seed vs single seed. Single plain ModernBERT-large seeds are high-variance at ~2.6k rows: re-running the same seed on a different Kaggle T4 allocation moved calib AUC 0.839 → 0.815, the calib-transfer threshold 0.80 → 0.96 and test recall 0.70 → 0.44, turning a significant ensemble win into a single-seed tie with Laya. Make training deterministic (`torch.use_deterministic_algorithms`, fixed `seed` + `data_seed`, `CUBLAS_WORKSPACE_CONFIG=:4096:8`) and save weights from the run you score, so the model that ships is the model that was measured.
- A threshold belongs to one set of weights. Recompute it from THAT run's calib predictions before scoring anything (sealed test, KB shadow); a child that applies an earlier run's threshold to re-trained weights reports the wrong flag counts (here 107 vs the correct 73). Re-score a child's KB/flag numbers yourself from its prediction files.
- On Apple MPS, fp16 inference of ModernBERT-large was no faster than fp32 (slightly slower), with ±0.001 AUC. Ship fp32 there; fp16 is not a free speed-up on this hardware.
- A co-hosted gate does move LH02's llama.cpp reranker: p95 rose ~21 → ~28 ms (+32%) while a gate model ran. Small in absolute terms but report it, since the reranker sits on every memory lookup.
- Score every run yourself on the live-verified labels with a PAIRED bootstrap of ΔF1 vs the rule (pass iff CI lower bound > 0), across all seeds. Children used a looser "Δ > CI half-width" test, crowned a single-seed RLCD run as best-of-4, and scored on the original labels; on verified labels RLCD ≈ soft-CE on AUC (upstream Gate D: loss difference is seed noise). Prefer soft-CE: RLCD's temperature stays at the 5.0 clamp, and on 2 of 3 seeds no calib threshold reached P≥0.95, so it has no usable auto-drop operating point. Seed spread at 185 train rows was F1 0.70–0.79 and AUC 0.73–0.81 at 2k rows — never report one seed. When rescoring a child's run, recompute thresholds from the calib predictions yourself; a child's threshold choice can decide pass/fail on its own.
- Claude text-only labels are keep-biased: live verification of 150 rows flipped 22, all keep→drop (task directives, bare code/commands, generic advice, fragments, debug traces, stale facts). Put those categories into the teacher rubric explicitly.
- Secret scrubbing regexes miss non key=value shapes: `password <pw>` and `the <pw> credential`. Grep scrubbed files for password/credential/passwd and eyeball every hit BEFORE any upload; Kaggle cannot delete a single dataset version, only the whole dataset. Subagents echo found secrets into their summaries.
- A subagent's "same failure as upstream issue X" needs the same signature before you adopt it: the update-collapse issue scored at chance, while ours learned (AUC 0.81–0.87), so the right reading was under-training, not collapse. Take the mechanism (count optimizer updates), not the label.
- Label noise caps the score: upstream's teacher self-agreement was 0.735 and the fine-tuned model already exceeded it. Measure κ before blaming the model.
- "Was this fact later superseded?" is not learnable from one row of text. Frame staleness as a pairwise noul ("does new fact B supersede old fact A?") — every KB update yields a labelled pair.
- Input format beats data volume: upstream's browser-agent fine-tune gained more from restructuring what the model sees than from any data change. For the store gate, test `fact + date + newest related fact` against bare text before scaling rows.
- Templated or generated negatives teach the template: the model keys on the `Session:` prefix or on LLM writing style, not on the decision. Keep negatives verbatim from real sources and judge models on the hard subset.
- Escalating low-confidence cases to a bigger local LLM made upstream's results worse than the fine-tuned small model alone; don't add an LLM fallback without benchmarking it.
- Zero-shot Laya is a control. The README says it plainly; the paper's 96.7% came from 1.2M synthetic training rows, not from a base checkpoint.
- `Router.predict_batch` takes a list of `{state, questions, model, …}` dicts — not `(states, questions)`; `Agent.predict_batch` has a different shape.
- English checkpoint ships out-of-range temperature values; laya clamps to 0.5 with a RuntimeWarning — its confidences are uncalibrated until you fit temperatures yourself.
- Multilingual default `max_len` is 1024 and truncates silently; pass `--max-len 8192` for long states. For short facts 512 is enough and faster.
- `choice` questions with many options hit the option token budget (`head_max_len`, default 192): 58 labels → 24/58 correct at default, 34/58 at 384. Route by retrieval first, then judge pairs with `noul`.
- Ground truth mined from agent behaviour (e.g. which skill Claude loaded) encodes Claude's mistakes; a fine-tuned judge imitates, it does not exceed.
- The paper (single author, no code, anonymised comparators) is a pattern source, not evidence — treat every number in it as unverified.
- `laya` pins `transformers`; do not upgrade it inside the sandbox venv.
- Single-text classification is not Laya's niche, measured: on the store gate, with identical labels, splits and threshold rule, plain HF fine-tuning of the same ModernBERT-large backbone (soft-target CE, lr 2.5e-5, 4 epochs, effective batch 64, max_len 512) reached ensemble AUC 0.892 and recall 0.71 at P 0.965. Laya reached 0.825 and recall 0.51. ΔAUC −0.067, CI [−0.12, −0.02]. TF-IDF + LR tied Laya (0.828, 0.3 ms/row CPU); frozen bge-small + LR and a SetFit-style arm also tied. The internal ~10% calib holdout is NOT the cause (training on all rows left AUC unchanged); the remaining suspects are Laya's pretrained checkpoint and its transformer head (see the catch-up bullet in step 6). For a one-question yes/no over a single text, default to a plain fine-tune (or TF-IDF + LR when CPU-only), and keep Laya for structured, multi-question or pairwise inputs. Even there, it must win the attribution test.
- Labels are the lever, measured: replacing teacher-v3 hard labels (balanced accuracy 0.72 on a live-verified dev set) with soft targets = mean(drop votes of the verifier-prompt text-only labeller and the v3a skeptical keep-audit) lifted the sealed-test mean AUC from 0.77 to 0.818 (seeds 0.846/0.788/0.821; ensemble 0.829, oracle cov@P95 0.655), with the same data volume and budget. laya 0.4.7 soft-CE accepts probability targets through the gold `{probabilities}` schema, so 0.5 rows need not be dropped.
- Gold rows lose silently in a text dedup: a dev set sampled from the training pool was already in train with teacher labels, so adding its live-verified labels kept the soft copies and the gold was never used. When adding gold, gold wins the dedup. If a dev set will later serve as calib, sample it from rows that are NOT in train, or remove its texts from train first.
- Measured store-gate retrains on teacher-v3 rows (210 verified calib, sealed 150-row fresh test, ~77% drop): 2,182 rows × 4 epochs, 2,182 × 8 and 2,618 × 8 all land at mean AUC 0.75–0.77; a 9-seed ensemble gives AUC 0.77 and calib-transfer P 0.97 at drop recall 0.29. The teacher's own labels have balanced accuracy ≈ 0.78 on the same rows: the student has caught up with its teacher, so only better labels move it (see the plateau rule under Long autonomous programs).
- Measured fine-tune store gate (185 train / 86 test, verified labels, rule F1 0.640): LH02 soft-CE s0 F1 0.787; Kaggle soft-CE s0/s1/s2 ΔF1 +0.134/+0.063/+0.122, RLCD s0 +0.140 — 2–3 of 5 pass. Overall AUC ~0.84; hard subset AUC ~0.70, cov@P≥0.95 1–9% (not actionable). Kaggle 2×T4 ~2.7 min/seed vs LH02 MPS ~4.5.
- Measured zero-shot store gate (English, 296 rows): F1 0.03 at the 0.5 decision point, AUC 0.66 (CI 0.60–0.72) — weak signal, no usable operating point. Control only.
- Skill-routing labels mined from `state.db` are scarce: ~6% of prompts carry an explicit `skill_view` (73/1266 → 41 train positives). Too small for Laya fine-tune; SetFit or nothing.
- Candidate generation is the routing bottleneck, not the judge: live keyword `_search_skills` ceiling@10 0.15 vs cosine 0.41 on the same test prompts. Fix retrieval before adding any judge.
- Zero-shot relevance gate (Exp B, English): AUC 0.73, but precision at recall ≥ 0.95 was 0.325 vs the reranker-threshold baseline of 0.383. The reranker is the ceiling, so the read path is closed to base Laya. Multilingual was worse on both A and B.
- Regex garbage patterns matched 0 live KB rows (all junk is semantic), so the store-gate baseline is "no gate".
- Full Laya fine-tune on this CPU is impractical: one timing probe exceeded 7 min. Use LH02 MPS/GPU or `laya-train --freeze-encoder`, or run SetFit.
- laya-ai.com / console.laya-ai.com is a third-party hosted reseller ("not affiliated with ConvAI"). No API key is needed, since the weights are local. Its guides document `laya-train` (0.3.28+): `--dry-run`, `--freeze-encoder`, `--loss soft-ce`, `--target-error`, `--eval` → train_report.json.
- Upstream typed-decisions benchmark: base `laya` 0.362, below the majority class (0.461). Fine-tuned 0.766 on 1,200 cases (~30k questions, 4–5 h on 2×T4). ~200-row sets are SetFit scale.
- Benchmark candidates for anything on the per-turn path (unified_search, prefetch, skills store) stop at a pass/fail recommendation; swapping into the live file needs a separate explicit go-ahead even when every bar passes. Andrew rejects changes that can affect agent responsiveness unless necessary.
- Same pattern seen in the semantic skills store: a cosine floor (0.55) cut half the true positives because the positive and negative cosine distributions overlap (neg p90 0.62, pos median 0.60). Cap slots rather than floor scores.
