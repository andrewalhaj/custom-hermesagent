# Public README for the operator's repos — shape, verification, PDF render

Applies to every README in a repo that is or will be public (custom-hermesagent, hermes-dispatcher, …). Delegate the draft; verify it yourself; the user reviews the PDF.

## Shape the user wants

- Simple and professional. Lead with what the repo is and why it exists, then ONE Mermaid diagram, components in short tables (≤ 4 columns), the ~10–15 settings someone would actually set (link to the code for the rest), status/limitations, license. Target 100–180 lines.
- NO Quick Start, NO "running the tests" section, NO "relationship to upstream" section — the user removed all three. Upstream and sibling repos get one linked sentence in the intro or a components row.
- Cut internal history: dates, "retired/excised", benchmark minutiae (one sentence or a link), exhaustive caveat lists, operator workflow, other agents, per-test counts.
- Public safety on top of the scrub rules: no host aliases at all (not even LH01/LH02 — write "a second machine with a GPU" / "a metrics host over SSH"), `~/.hermes` never `~/`, no numeric chat ids, no `0.0.0.0` (say "all interfaces"). Gate: `grep -niE '([0-9]{1,3}\.){3}[0-9]{1,3}|~/|<employer terms>|apikey_|sk-ant|ghp_|LH0[12]' README.md` prints nothing AND `gitleaks detect --no-git -s README.md` passes — run both yourself after any worker edit.
- Describe switches by mechanism, not verdict: "enabled per environment with an API key and one flag; without them the local path applies" — never "optional", which reads as unimportant for something that is on in production. Same for fallbacks: name the default stage and call the fallback "degraded mode".
- Mention the repo has no LICENSE file if true, and offer to add one before the push.

## Verify against the live tree (claims AND omissions)

1. Claims: for every table row and number, run the receipt — `git ls-files <dir> | grep -c SKILL.md` for skill counts, `ls plugins/*/guards`, `grep -rl <ENV_VAR> scripts plugins` for every variable listed (drop vars nothing reads), `grep -o '"react": *"[^"]*"' app/package.json` for versions, `/proc/<MainPID>/environ` for what is actually on, cron/jobs.json for schedules. Do not describe what a remote database function does internally unless its source is in the repo — state only what its output proves.
2. Omissions: diff the tracked tree against the doc — `git ls-files scripts | grep -E '\.(py|sh)$' | grep -v test` vs the names in the README; cron entry points and shared libraries are the usual misses. Everything live gets a row; known-dead files (purge candidates) are left out, not documented.
3. Tracked-ness: every directory the README names must be in `git ls-files` — a locally-built `ops/` that was never added is a dangling reference for every cloner. Check symlinks the same way.
4. Reversal check: a README drafted while a config change was in flight describes that window. After any revert, grep the docs touched since for the reverted claim (diagram labels and env tables included, not just prose) and fix the sentence in place.
5. Scheduled-vs-manual: a script that exists is not a job that runs — check cron/jobs.json before writing "every 4 h"; write "manual (`--apply`)" when nothing schedules it, and flag the gap to the user.

6. Named services need their knob: every external service the prose names (a reranker on another host, an embedding endpoint, a hosted judge) must have its URL/key variable in the config table — reviewers ask "what serves it and which env var" first. Describe privacy switches by WHAT they withhold (a regex of subnet prefixes / employer names / hostnames; secrets are already masked upstream), not just that they exist.
7. Schema reproducibility: if the README describes database objects (vector columns, indexes, search functions), the SQL must be in the repo. Dump it from the live project (Management API: `POST /v1/projects/<ref>/database/query` with `pg_get_functiondef`, `pg_indexes`, `information_schema.columns`) into `scripts/<pkg>/sql/<table>.sql` as idempotent DDL — and redact plpgsql function bodies: webhook triggers carry the dispatcher URL and bearer secret as string constants, so the dump script replaces them with placeholders and asserts the placeholder is present before writing. Run gitleaks on the SQL dir.
9. Safety claims are per component, never blanket: before writing "every component fails open", read each guard's loader tier — a required guard (gateway refuses to start without it, unattended gated writes blocked) fails CLOSED, and a reviewer will read a blanket fail-open as "destructive commands go through on error". Name the exception in the same sentence.
10. State a negative once: a decision that something is NOT the production path (a benchmarked-but-unshipped backend) lives in one paragraph; the config table row just lists the allowed values. Scripts table: two tables — scheduled jobs with a Schedule column (from cron/jobs.json), and shared code/tools — a manual-only script never sits under "Scheduled". Flag naming inconsistencies (hyphen vs underscore filenames) to the user instead of silently renaming: renames change cron/jobs.json.
8. Code is part of the surface, not just prose: grep tracked code for employer tokens too (the scrub grep over README passes while a hard-coded tenant regex sits in a `.py`). Move such literals to an env variable with an empty default.

## Render to PDF (no TeX on this host; Kroki returns 500s)

`scripts/render_readme.py <README> <assets-dir> <out.pdf> [css]` (in this skill) is the working recipe: for each ```mermaid block it writes `.mmd`, renders with `npx -y @mermaid-js/mermaid-cli ... -p pp.json` (`{"args":["--no-sandbox"]}` — headless chrome refuses to launch as root without it), substitutes an ABSOLUTE png path (a relative one resolves against the HTML's directory and wkhtmltopdf silently embeds nothing), then pandoc (`-f gfm-implicit_figures`, or a lone image becomes a captioned figure and the alt text "diagram" prints under it — the user read that as a broken image) → HTML → wkhtmltopdf. Verify with `pdfimages -list out.pdf` (one image per diagram) and a `pdftoppm` page + vision check once. Re-run after every edit; post the PDF with `MEDIA:` on Telegram. Never leave the only copy of the recipe in `cache/scratch` — it is pruned after 24 h.
