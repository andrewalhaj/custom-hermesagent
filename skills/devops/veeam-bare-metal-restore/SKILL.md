# Veeam Agent bare-metal restore (Dell laptops)

Recovery media = WinRE boot tool, not an OS image. Booting it should land on the green menu (Bare Metal Recovery / WinRE / Tools); "Windows never loads" from it is expected. A .ppkg cannot be extracted from it.

## Boot pitfalls (check in this order)
1. **Disk on USB-C/Thunderbolt port:** Dell ships Thunderbolt Boot Support + TBT pre-boot modules OFF -> device invisible in F12. Enable both or use USB-A. Turn back off after (DMA risk).
2. **Rufus-written media on NTFS** adds a tiny UEFI:NTFS FAT partition (third-party-CA signed). Needs Dell "Enable Microsoft UEFI CA" = Enabled; may still be rejected by Secure Boot revocations. Prefer Veeam > Create Recovery Media > Removable storage (FAT32, MS bootloader) or Rufus GPT/UEFI/FAT32.
3. Fastboot = Thorough, USB Boot Support on. Manual entry: Boot Sequence > Add Boot Option > \EFI\Boot\bootx64.efi.
4. Suspend BitLocker (`Suspend-BitLocker -MountPoint C: -RebootCount 3`) before changing Secure Boot settings; have recovery key from Entra/Intune.
5. **Media BSODs while booting (SYSTEM_SERVICE_EXCEPTION, `win32kfull.sys`)** = WinPE itself crashing (the blank target disk cannot be what is booting). Cause not established. Retry after a hard power-off, then the other USB port; if a BIOS storage-mode switch (RAID On <-> AHCI/NVMe) immediately preceded it, flip it back as a test before anything else; note whether it dies before or after the green Veeam menu. Repeatable -> rebuild the media on a **separate stick**: Veeam Agent > Create Recovery Media > Removable storage (FAT32, no Rufus), tick 'include hardware drivers', on a Win11 build >= 26100.9445 / 26200.9445 (older 2026 WinRE builds have a known Veeam media defect, KB4885). A separate stick is also what makes the diskpart rule below safe.

## Find the backup and check whose it is
- Backups live at `<backup drive>:\VeeamBackup\Job <COMPUTERNAME>\`: the `.vbk` is the full backup (its file size is the backup size; compressed, so far smaller than used space on C:), the `.vbm` is metadata. The job folder name is the source computer name; compare it with the PC being restored before starting. `VEEAMRE` is the drive's volume label, not a folder.

## Disk mapping
- "Unable to auto match disks" / "Cannot find original disk layout" = target disk differs from backup. **First compare the backup's disk/C: sizes with the target**: mismatch means drive was replaced OR wrong machine's backup (identity clash). Confirm computer name before restoring.
- **Only the external backup disk listed (e.g. Disk 0 = VEEAMRE 1.8 TB), internal NVMe absent** -> Dell BIOS is in **RAID On** (Intel VMD): the NVMe sits behind the VMD controller and WinPE has no driver for it. This is not a RAID array and adding RAID (RAID 1 etc.) changes nothing about auto-match: Veeam keys on the signature of whatever Windows sees as the disk, and a mirror just moves the single-drive-failure case to an RST rebuild instead of a restore. Fix: Dell support (service tag) > Storage > Intel RST driver; extract; copy the folder holding `iaStorVD.inf` (VMD) / `iaStorAC.inf` (older) **onto the VEEAMRE drive itself** (already visible in WinPE, no second stick); Disk Mapping > Load driver > Load Driver > pick the .inf > Install, leave 'Inject these drivers' ticked. Prefer this over switching BIOS to AHCI: the backup was captured on RAID On, so the restored Windows must boot on RAID On or it stops at INACCESSIBLE_BOOT_DEVICE. If AHCI is used for the restore pass, set RAID On back before first boot.
- Manual mapping: target = internal disk, never the external backup disk; restore whole disk; **tick every partition incl. the ~100 MB EFI one**. Veeam may pre-tick only C:, which yields an unbootable restore.
- **Verify the Disk Mapping preview before Next:** the target disk row must show ALL backup partitions (EFI ~100 MB, Recovery, C:). If it shows only C: + a few GB unallocated: click **Customize disk mapping** (bottom of the wizard), right-click the target disk in the left pane -> **Apply Backup Layout** (official name per Veeam user guide, step 10; other entries are Apply Disk Layout / Erase). That writes the whole disk (EFI + MSR + Recovery + C:) instead of a lone volume, wiping whatever is on the target. The right-click target is the **disk box on the far left** ("Disk 0 / 953 GB"); right-clicking a partition bar shows nothing and reads as 'right-click fails'. WinPE's touchpad driver often ignores the right-click zone: left-click the disk box, then Shift+F10; two-finger tap; else a USB mouse. After Apply Backup Layout nothing needs ticking: the main Disk Mapping page lists every backup volume ticked with Restore = Auto (EFI shows as 'Basic data partition' ~100 MB; MSR never appears as a row). Verify instead: no row targets the backup disk, widen the Restore column to read the target, Summary says N volumes to the internal disk. Auto-match ("Entire computer" mode) is keyed to disk identity/size/partition table: there is no setting that makes it succeed on a replaced disk; Apply Backup Layout is the one-click equivalent. Also check any extra internal disk (e.g. second SSD 'Storage E:') isn't being overwritten unintentionally.
- BitLocker: locked target -> Unlock to keep encryption, or OK = wipe + restore unencrypted. Resize/new disk = unencrypted. A target C: shown as filesystem 'unknown' (purple) is a BitLocker volume WinPE cannot read, not a damaged disk.
- **Restore log: 'Updating disk partition structure' OK, then 'Restoring \\?\Volume{GUID} ... A device which does not exist was specified / Failed to open volume'** = WinPE's Mount Manager did not register the freshly created partitions as volumes, so Veeam cannot open them by GUID. Not a backup or mapping fault. The partition table was already rewritten, so the old OS on the target is gone regardless; there is nothing left to preserve. Retry order (not yet verified end-to-end; mechanism-driven): **unplug the backup drive first**, then Tools > Command Prompt > `diskpart` / `list disk` (the only disk left must be the NVMe; confirm by size) / `select disk N` / `clean` / `rescan` / `exit`, replug, rerun Bare Metal Recovery > Manual > Apply Backup Layout on the now-blank disk; if identical error, do the restore pass with BIOS on AHCI/NVMe (disk is native to WinPE, no runtime driver), then RAID On before first boot. Falling back to tick-C:-only + hand-built ESP is last resort: it creates and opens a fresh partition through the same path, and leaves no Recovery partition.

## diskpart on the media: disk numbers shift
- With RAID On and no VMD driver loaded, the NVMe is invisible and the **USB backup drive is Disk 0**; load the driver and it becomes Disk 1; reboot the media and it is Disk 0 again. A `select disk 0` / `clean` written for the NVMe wipes the backup drive's GPT. Hard rule: **the backup drive is unplugged before `diskpart` starts** (needs media on a separate stick); a size check in chat is not a guard, it gets skipped under pressure. If it must stay attached: `list disk` + `list volume`, and the selected disk's size must be the NVMe's with VEEAMRE not on it.
- Recovery: `clean` zeroes the first/last ~MB (partition table); whether sector 2048 (NTFS boot sector) survived is unverified (TestDisk `P` -> "Can't open filesystem. Filesystem seems damaged" even on a clean host, but three early Quick Searches did recognise NTFS at 2048, so the failure may be a dropped $MFT read instead). Check it directly with HxD (Tools > Open disk > physical disk, read-only): Search > Go to in **hex, byte** units: `100000` = sector 2048, `1D1C1005E00` = sector 3907026991 (backup boot sector); intact = `EB 52 90 4E 54 46 53` / `.R.NTFS`; typing `2048` there lands on sector 16 (zeros, meaningless). (Earlier wording: the label/blocksize TestDisk shows come from the backup boot sector at the volume's last sector, 3907026991 on this 2 TB Seagate). Files are intact; the fix is partition table + Backup BS, below. On another PC: Disk Management shows it Not Initialized / Unallocated (expected), **cancel every Initialize/Format prompt**. TestDisk 7.2 win64 (cgsecurity.org, `testdisk-7.2.win64.zip`) as admin -> Create -> pick the 1863 GB disk -> **EFI GPT** (not the default Intel/PC) -> Analyse -> Quick Search -> on the ~1.8 TB NTFS entry press **P** and confirm `VeeamBackup` lists (proof before any write) -> mark P primary -> Write -> Y -> replug. Deeper Search if Quick finds nothing.
- **Reads work, writes fail** on a bus-powered 2.5" USB drive (TestDisk finds both partitions but `Write` -> "Partition: Write error"; `P` -> "Can't open filesystem"; diskpart `list disk` intermittently shows the drive as **0 B**; a scan wedges at 99% or throws an early read error; diskpart `convert gpt` -> "I/O device error") is mostly the link, with one exception: **TestDisk "Partition: Write error" alone is Windows** blocking raw writes to an online disk that has volumes (it recurred on a healthy host/port where diskpart `convert gpt` succeeded). Fix: `diskpart` > `select disk N` > `offline disk` > exit, then TestDisk Write / Advanced > Boot > Backup BS, then `online disk`. `I/O device error` from diskpart is device-level. Writes draw more current than reads, so a weak USB-C port or dock browns the bridge out exactly on writes; a genuinely failing drive looks the same. **Confirmed outcome: it was the USB-C dock.** Every failure (0 B, read error, Write error, I/O device error, empty Quick Search) happened with the drive on a Dell dock; the same drive on another PC's direct port ran Quick Search in seconds and listed both partitions. First move for any flaky external drive is a different host on a direct port, before SMART, before any 'drive is failing' claim. The intermittent "Read error at lba=..." lines (305234, 433754, 514079: a different sector every pass, never repeated) were NOT the platters: CrystalDiskInfo on a direct port (ST2000LM007 behind the Seagate bridge, SMART passes through there, not via the dock) read 05/C5/C6/C7 = 0, BB = 0, 2607 h, one Command Timeout = Windows UASP timing out TestDisk's single-sector reads. Same-LBA-every-time is media; moving LBAs is the host stack. Still copy with `robocopy /E /Z /R:20 /W:3 /J` so a dropped read resumes instead of restarting. Discriminate with two readouts before any verdict, and give Andrew the readouts, not the inference: CrystalDiskInfo (portable) Reallocated / Pending sectors, and Event Viewer > System source *disk* (event 7 = bad block on platters; 153/157 = bridge reset / surprise removal). Then: (a) try the Write from a different host with a USB-A port or a powered hub; (b) if the device still errors, stop writing to it and extract read-only instead: TestDisk `P` on VEEAMRE -> `VeeamBackup\Job <name>\` -> `C` to copy `.vbk` + `.vbm` to a local folder (untested here but TestDisk's documented path), or a Linux live USB on the blank target laptop with `ntfs-3g -o ro,offset=1048576` / ddrescue. Restore then runs from the copy: recovery media reads backups from an SMB share. Known geometry if a partition must be recreated by hand (only on a device that writes cleanly): VEEAMRE = NTFS from sector 2048 (`offset=1024` KB) spanning the disk; RUFUS_BOOT = 1 MB EFI at the tail, expendable; diskpart path = `convert gpt` -> delete the auto 16 MB Reserved -> `create partition primary offset=1024` -> `list partition` must read Offset 1024 KB -> `assign`; never pass `size=` (shorter than the NTFS volume won't mount; longer is fine for Windows). But TestDisk **Advanced only offers Boot** (needed for Backup BS) when the partition's last sector equals the filesystem's last sector, because it looks for the backup boot sector there: a diskpart whole-disk partition (end 3907028991 vs FS end 3907026991) shows only Type/Image Creation/Quit. So let TestDisk Write the table (offline disk) rather than diskpart. Win11 `convert gpt` auto-creates a 15 MB Reserved at 17 KB: delete it first. Dead ends on Windows: `New-Partition -Offset -Size <bytes>` -> "Access to a CIM resource was not available" whenever diskpart/TestDisk/Explorer holds the disk; .NET `FileStream('\\.\D:')` reads -> "Incorrect function"; `chkdsk` refuses RAW. The vision tool fails on PowerShell screenshots: ask for pasted text. Don't rescan a flaky drive to re-find numbers you already have; `L` reloads TestDisk's last found list.

## Restored but no "Windows Boot Manager" in F12 / Boot Sequence
Symptom: boot list shows only USB + NIC/HTTPS entries while BIOS > Storage still lists the NVMe. Dell **Add Boot Option** file browser = fast diagnostic: it lists every partition the firmware can read; the OS disk's ESP absent there = nothing to point at yet. Read the `HD(n,GPT,...,sectors)` device path on each entry: an entry named after a data volume (e.g. "Storage") whose sector count matches the second SSD is not the OS disk, so don't add it. Boot the Veeam USB > Tools > Command Prompt > `diskpart` > `list disk` > `select disk N` > `list partition`. Only MSR 15 MB + C: with a few GB free = the C:-only mapping trap. Fix in place, no re-restore:
```
select disk N
create partition efi size=260      (free space is usually there; else select volume C -> shrink desired=300)
format quick fs=fat32 label=System (exactly fat32; fs=32 -> "The file system is incompatible")
assign letter=S
list partition
exit
bcdboot C:\Windows /s S: /f UEFI   (-> "Boot files successfully created.")
wpeutil reboot                     (pull the USB as the screen goes black)
```
If `create partition efi` ran twice during a typo loop, `select partition <unformatted one>` + `delete partition override` before bcdboot. The check must run on the TARGET booted from the media: plugging the backup disk into one's own laptop shows that laptop's disks (the diskpart banner hostname says which machine you are on). First boot shows "Getting devices ready" and may reboot once: normal PnP re-detection. Recovery partition stays missing (`reagentc /info` = Disabled); rebuild later.

Guidance style when Andrew types from phone photos at a BIOS/WinPE prompt: one exact line per step, Enter after each, state the expected output; run vision_analyze on the photo to read the command as typed before diagnosing an error (auto-captions paraphrase). A destructive step (`clean`, Write, Apply Backup Layout) gets its guard as a physical action (unplug the other drive) or a required photo of `list disk` before the command, never as 'expect N GB' prose. Hardware verdicts ('drive is failing') only with the checkable readout (SMART, event IDs) attached; he will push back on inference, correctly.

## After restore
- Unplug the recovery disk before reboot (else it boots back into Veeam). No "Windows Boot Manager" entry: see section above (bcdboot from UEFI-booted WinPE also writes the NVRAM entry; Dell Add Boot Option is only the fallback).
- Extend C: if target disk was larger; TBT boot / UEFI CA back off; domain trust: `Test-ComputerSecureChannel -Repair`.
- **Re-baseline the backup.** Once the machine boots from the hand-built ESP, run a fresh full backup from Veeam Agent before BitLocker: the new restore point matches the drive's actual layout (MSR + C: + System), so future restores to THIS disk auto-match in Entire-computer mode and write every partition. Any future drive swap still drops to manual mapping -> Apply Backup Layout. Never re-restore the pre-fix backup onto a replaced disk via tick-boxes; it reproduces the C:-only mapping (via Apply Backup Layout it is fine, the whole disk is written). Root cause to state in write-ups: replaced disk -> auto-match fails (signature/size) -> manual mapping pre-ticks C: only -> volume restored, not disk -> reported as success.
- **WinRE first, then BitLocker.** A C:-only restore leaves no Recovery partition and no `Winre.wim` (`reagentc /info` = Disabled, blank location; `Test-Path C:\Windows\System32\Recovery\Winre.wim` = False). Put it back before touching BitLocker: on another Win11 laptop `reagentc /disable` (drops Winre.wim into `C:\Windows\System32\Recovery`), copy it to USB, `reagentc /enable` there again; on the target copy to `C:\Recovery\WindowsRE\`, `reagentc /setreimage /path C:\Recovery\WindowsRE`, `reagentc /enable`. Alternative source: `install.wim` from a Win11 ISO via `dism /Mount-Image ... /ReadOnly`. Winre.wim is hidden+system (invisible in Explorer; verify with `Get-ChildItem D:\Winre.wim -Force`), and a slow USB stick keeps writing after Copy-Item returns (Task Manager removable disk at 99%): wait for 0% before ejecting or `dir D:` hangs.
- BitLocker comes back fully off (new layout = unencrypted write). Enable from PowerShell, not the Control Panel wizard (the wizard's reboot hardware test fails on a rebuilt boot path): `Enable-BitLocker -MountPoint C: -EncryptionMethod XtsAes256 -UsedSpaceOnly -TpmProtector -SkipHardwareTest`, then `Add-BitLockerKeyProtector -MountPoint C: -RecoveryPasswordProtector`, then `$id = (Get-BitLockerVolume -MountPoint C:).KeyProtector | Where-Object KeyProtectorType -eq 'RecoveryPassword' | Select-Object -ExpandProperty KeyProtectorId` and `BackupToAAD-BitLockerKeyProtector -MountPoint C: -KeyProtectorId $id` (two steps; a one-line pipeline typed from a phone gets mangled and prompts for KeyProtectorId). Intune may re-apply within the hour; check `manage-bde -status C:` before doubling up.
- "BitLocker could not be enabled / encryption key cannot be obtained, verify TPM" or `FileNotFoundException` from `Add-TpmProtectorInternal` after a restore is usually NOT the TPM. Diagnose in this order, one command per line: `Get-Tpm | Format-List *` (TpmReady/TpmOwned True, ManagedAuthLevel Full = healthy; clear only if not), `Confirm-SecureBootUEFI`, `Get-ItemProperty HKLM:\SOFTWARE\Policies\Microsoft\FVE` (blank = no Intune/GPO pin), `reagentc /info`. BitLocker events 893/813/881 (TCG log / Secure Boot / boot-manager signature) are PCR7 fallback warnings, not the blocker. Healthy TPM + Secure Boot on + no policy + WinRE missing -> restore WinRE (above) and retry; if it still fails, refresh boot files from inside Windows (`mountvol S: /s`, `bcdboot C:\Windows /s S: /f UEFI`, `mountvol S: /d`) so the boot manager signature matches the firmware db.

## Disk-number shift: `clean` can hit the backup drive
In WinPE on RAID On without the RST driver loaded, the NVMe is invisible and the external backup drive becomes **Disk 0**. Any `diskpart` sequence written against "Disk 0 = internal" then wipes the backup drive's partition table. Rules: unplug the backup drive before any diskpart on the target (keep recovery media on a separate USB stick so this is possible); `list disk` and confirm the size on screen before `select`; never pre-state the disk number from a previous boot.

## Recovering a backup drive after a wrong-disk `clean` (done 2026-10-21, Seagate 2 TB, Rufus GPT)
- `clean` zeroes the first and last ~1 MiB **including sector 2048**, i.e. the NTFS boot sector of a 1 MiB-aligned partition. Data beyond it is untouched. TestDisk still lists the volume (from the backup boot sector at the volume's last sector) but `P` says "Can't open filesystem" and Advanced shows no NTFS/Boot entry.
- Diagnose with HxD (Tools > Open disk, read-only): Go to hex byte offset `100000` (sector 2048) and `<(start+size-1)*512 in hex>` (last FS sector; for this drive `1D1C1005E00`). Zeros at 2048 + `EB 52 90 4E 54 46 53` at the end = boot sector only.
- Windows blocks TestDisk's raw partition-table writes ("Partition: Write error") on both online and uninitialised disks, on every host tried; `convert gpt` via diskpart works. Fix path that worked: diskpart `convert gpt` > delete the auto 15 MB Reserved partition > `create partition primary offset=1024` > `assign`; then diskpart `offline disk`; HxD opened **not** read-only > Select block at the backup boot sector, length `200` hex > Copy > Go to `100000` > **Paste write** (Ctrl+B, never Paste insert) > Save; `online disk`; Explorer mounts the volume. Partition end a few thousand sectors past the FS end is harmless.
- TestDisk "Read error at lba=…" on random, different sectors each pass + "Partition: Write error" is NOT a failing drive by itself: Windows UASP timeouts on single-sector reads, and docks (shared bus power, own bridge) made it worse (drive dropped to 0 B in `list disk`). Direct host port = clean scans. **Check SMART (CrystalDiskInfo: 05/C5/C6/C7) before telling Andrew a drive is failing**; a clean SMART ended a wrong diagnosis. Quick Search that "hops to 99%" is normal (found the volume, skipping to the disk tail); Deeper Search finds filesystem images inside files (boot.wim, floppy images) as junk partitions — never write those.
- .NET FileStream on `\\.\D:` fails with "Incorrect function" on volume reads; Storage cmdlets (`New-Partition`/`Remove-Partition`) throw "Access to a CIM resource was not available" while diskpart, Explorer or a format prompt holds the disk — diskpart + HxD is the reliable combination.

## Restore failed: "A device which does not exist was specified. Failed to open volume"
After "Updating disk partition structure" succeeded. WinPE did not enumerate the freshly created volumes (seen with runtime-loaded VMD/RST driver on a previously BitLocker'd target). Try: diskpart `clean` the TARGET (size-verified) + `rescan`, rerun Apply Backup Layout; else switch BIOS to AHCI/NVMe for the restore (disk shows natively, no Load driver) and set it back to RAID On before first boot (or whichever mode the backup source used; wrong mode = INACCESSIBLE_BOOT_DEVICE, flip and retry, no data impact). Recovery media that BSODs on boot (`SYSTEM_SERVICE_EXCEPTION win32kfull.sys`) repeatedly = rebuild it on a Win11 box with the Sept-2026 update (KB4885: Jun–Aug 2026 WinRE is broken), Removable storage, FAT32, not Rufus.

## Giving PowerShell/diskpart instructions over chat
- One command per message block, no trailing `# comments`: PSReadLine pastes a multi-line block as one buffer and a `#` on the first line comments out every line after it, so only the first command runs (you'll see `>>` continuation prompts and a single "Operation Successful"). A lone `>>` prompt means an unfinished line: Ctrl+C and retype.
- Quote braces for native commands: `bcdedit /enum '{bootmgr}'` (PowerShell parses bare `{}` as a script block).
- Never paste a recovery password back into chat; treat one shown on a photo as exposed and rotate after the TPM protector is in place.
