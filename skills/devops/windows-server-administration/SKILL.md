# Windows Server / Active Directory administration

## When to Use
DNS records, domain controller tasks, or other Windows Server role work on the employer's on-prem servers, usually from a screenshot or a forwarded Teams request. Grow this skill with a section per role (DHCP, GPO, AD users) as those come up.

Andrew works on the employer's domain controllers over RDP and sends screenshots or Teams requests (often from the IT manager). He is the admin; no approval gates. Answer with the GUI path and the PowerShell equivalent, then a check command, its expected output, and what each failure means.

## Procedure
1. **Read the screenshot's exact values** with `vision_analyze` before saying "looks right". Hostnames like `wly7rl` vs `wly7rt` are often misread; compare letter by letter against the request.
2. **Say which DNS view the request touches.** The employer runs split-horizon DNS: `<ad-domain>` is hosted internally on the DCs (AD-integrated) and publicly at the registrar. A record added only at the registrar won't resolve on the office LAN/VPN; internal clients need the same record on the DC zone.
3. **Do the change.** GUI: Server Manager → Tools → DNS → Forward Lookup Zones → zone → right-click → New Host (A) / New Alias (CNAME); leave "Allow any authenticated user to update" unticked (static record, not dynamic) and leave "Create associated PTR" unticked for IPs outside the internal ranges (Azure/public — no reverse zone exists). PowerShell:
   `Add-DnsServerResourceRecordA -ZoneName <ad-domain> -Name <host> -IPv4Address <ip>`
   `Add-DnsServerResourceRecordCName -ZoneName <ad-domain> -Name <alias> -HostNameAlias <target>`
   A CNAME can't share a name with any other record; "already exists" = remove the stale A record first.
4. **Verify on the DC:** `Resolve-DnsName <fqdn> -Server 127.0.0.1` should show the CNAME chain, then an IP. A CNAME with no final IP = mistyped target. Then test from a client with no `-Server` (what users get); `ipconfig /flushdns` if a client caches the old answer.
   "DNS name does not exist" from a client right after adding is normally not a failed add: the client asked the *other* DC (first in its list) before AD replication carried the record over, then cached the NXDOMAIN. Query each DC explicitly (`Resolve-DnsName <fqdn> -Server <dc1-ip>` / `-Server <dc2-ip>`); one yes + one no = lag → `repadmin /syncall /AeD` on the DC that has it, then `ipconfig /flushdns` on the client. Both no with the record visible in DNS Manager = wrong zone. Both DCs still differing after a sync = broken replication (`repadmin /replsummary`) — a real finding, every change is landing on one DC.
5. **Hand back the next owner's step.** For CNAMEs to `*.azurewebsites.net`: an Azure "404 Web Site not found" or a certificate error over https means DNS is done and the App Service still needs the custom domain + certificate bound. Flag targets that look wrong for the purpose (e.g. a `-dev` app behind a production name). Offer a one-line reply for the requester.

## Entra / hybrid identity
- On-prem AD is authoritative; Entra Connect (PHS) runs on **the Entra Connect server** (hostname: memory_search "Entra Connect sync server hostname"). Connect Health agent is not installed, so the portal says "No servers found" - find the sync server from the MSOL_ account description, no RSAT needed: `([adsisearcher]'(&(objectClass=user)(sAMAccountName=MSOL_*))').FindAll() | % { $_.Properties.description }`.
- Password resets go in AD, not Entra (no writeback). PHS health on the sync box: `Get-ADSyncAADPasswordSyncConfiguration -SourceConnector <ad-domain>`, `Get-ADSyncScheduler`, Application-log events 656/657 from *Directory Synchronization*.
- Lost Authenticator (user deleted/restored the app - work accounts never survive restore): admins cannot issue a QR. Delete the stale Authenticator method on the user, issue a one-time Temporary Access Pass, user re-registers at aka.ms/mysecurityinfo -> Add method -> Authenticator. Adding from the app's own "+" is the path that loops.
- Read sign-in logs before blaming MFA: 50072 = enrollment required (clear worked), 50074 = MFA required/no method (loop), **50126 = wrong password** - repeated 50126 means mistyped/stale password, not an MFA problem. Microsoft Account Controls v2 = mysecurityinfo; Microsoft Authentication Broker = the Authenticator app itself. Before calling it a sync desync, confirm the account is plain in ADUC (Account tab: no must-change-at-next-logon, not locked) and Connect Health shows a recent error-free cycle; then a reset in AD with must-change UNticked (the cloud cannot satisfy that flag -> 50126 forever) settles it in ~2 min.
- **Partner-branded sign-in page (a customer or supplier name) = the partner's tenant.** The user is a B2B guest there; after your tenant authenticates the password, the partner's Conditional Access demands MFA and guests register it separately in that tenant unless the partner trusts inbound MFA. Your External Identities > Cross-tenant access page only shows your outbound side and cannot tell you whether they trust you. Fix the home-tenant MFA first, then read the partner attempt in sign-in logs: "satisfied by claim in the token" = they trust it; a register prompt = second Authenticator entry in their tenant; a hard block = their admin. Nothing on your side fixes a partner-tenant block.
- Reading AD from the laptop: DC list `nltest /dclist:<ad-domain>`, current DC `$env:LOGONSERVER`; module `Add-WindowsCapability -Online -Name Rsat.ActiveDirectory.DS-LDS.Tools~~~~0.0.1.0` (also installs ADUC/`dsa.msc`). If `Get-ADUser -Properties *` returns blank values for `Enabled`/`pwdLastSet` even as Domain Admin, stop debugging the module: RDP to a DC and read the Account tab in ADUC, which is authoritative. The NetBIOS domain is not derivable from the DNS name — check `$env:USERDOMAIN` (pre-2000 logon names).
- Flag, don't fix today: "Password never expires" + "User cannot change password" on a human account is a service-account pattern. Hybrid status of a device: `dsregcmd /status` (`AzureAdJoined` + `DomainJoined` both YES = hybrid-joined); identity is already hybrid via PHS, device join/writeback/Intune are the layers that may be missing and each needs the P1/Intune licence check (`Get-MgSubscribedSku`) first.

## Endpoint onboarding (no Intune yet)
- **Scope first:** ask whether the package must *join + install* or *install only* before explaining enrollment — Andrew's default ask is "just the programs"; a join/Intune-heavy answer to an apps-only request gets cut off. Apps-only PPKG = skip the Account Management page (its `Contoso\ScottLock` fields are grey placeholders; leave blank, Next), and say plainly it is equivalent to an `install.cmd` on the stick — PPKG only earns its keep as a single trust-prompted file for non-admin hands; `winget export/import` covers the commodity apps with no installers to collect.
- Default path: PPKG authored in Windows Configuration Designer, applied at OOBE; Autopilot is the project, imaging is the last resort. A `.ppkg` is never "extracted" from a laptop and a used laptop is never the image reference — say so when the request conflates them.
- The PPKG join credential is a dedicated `svc-domainjoin` in the Service Accounts OU with Create/Delete Computer objects delegated on the laptops OU only; never an admin account, never the default Users container. The account's *location* and the devices' *landing OU* are two different objects — the desktop wizard has no OU field, so joins land in `CN=Computers` (a container: no `gPLink`, no GPO, usually outside Entra Connect scope) until `redircmp` points the default elsewhere.
- Build steps (wizard vs advanced), `redircmp`, delegation ACL list, service-account hardening, RSAT/`runas /netonly`, imaging tool choice, and turning an installed-programs dump into a software standard: `references/endpoint-onboarding.md`.

## New server: picking a static IP (work LAN)
- Authority is the DHCP server, not a ping sweep: `ipconfig /all` on any client names it (`DHCP Server` line); DHCP console → IPv4 → Scope → **Address Pool** shows the exclusion ranges — servers live inside an exclusion by convention (employer-specific scope layout is not in this file: `memory_search "DHCP scope servers low block broadcast domain"`).
- Taken list = DNS A records **plus** a sweep, because ESXi hosts, SAN, iDRACs and switches are static with no A record (a datastore named `.<n>_datastore1_Local_` betrays a host at `.0.<n>`): `Get-DnsServerResourceRecord -ZoneName <ad-domain> -RRType A | Where-Object {$_.RecordData.IPv4Address -like "<server-subnet>.*"}` then `1..254 | ForEach-Object { $ip="<server-subnet>.$_"; if (Test-Connection $ip -Count 1 -Quiet -TimeoutSeconds 1) { $ip } }`; read vSphere Hosts → Summary for the management IPs too. Pick a gap above the gateway/DC cluster, next to sibling servers, confirm with `Test-NetConnection <ip> -InformationLevel Quiet` + `arp -a`, record it in the register.
- Network-profile prompt on a fresh server ("allow your PC to be discoverable") = **Yes** (Private, becomes Domain after join); No = Public profile and RDP/app ports stay blocked.
- Rename **before** the domain join (`Rename-Computer -NewName <name> -Restart`) so AD/DNS register the final name once. A rename done after the join is still fine when the DC is reachable; verify instead of undoing: on the server `hostname` + `nltest /sc_query:<ad-domain>`, on the DC `Resolve-DnsName <name>.<ad-domain>` + `Get-ADComputer <name>`, delete the stale `WIN-xxxx` A record, move the object out of `Computers` into the servers OU. `nltest` failing → `Test-ComputerSecureChannel -Repair -Credential (Get-Credential)` then reboot. Firewall rules ticked only for Private silently stop working after the join (profile flips to Domain) — tick Domain+Private.
- Getting an installer (NinjaOne agent etc.) onto a VM: no USB passthrough — `mstsc` → Local Resources → Drives, or download it in the server's browser. Keep the downloaded filename intact: the NinjaOne installer carries its org token in the name and a renamed copy installs into no organization.

## Enterprise Wi-Fi (802.1X) — laptop only joins guest SSID
- Read the working profile first (on a laptop that connects): `netsh wlan show profiles name="<ssid>"` → Authentication WPA2-Enterprise, EAP type. The employee SSID (name: memory_search "employee Wi-Fi SSID network facts") = **EAP-TLS, Machine credential**: the laptop authenticates with its own computer certificate from the AD CA; no user prompt, no password. Guest SSID is a PSK and is walled off from the server VLAN (ALM/RDP/DC unreachable from it).
- Failing laptop: `certlm.msc` → Personal → Certificates → cert issued to `<laptop>.<ad-domain>` by the internal AD CA, Client Authentication, not expired. Missing/expired → it never auto-enrolled or renewed: `gpupdate /force` + `certutil -pulse` **with a DC reachable**, refresh, cert appears within a minute, SSID connects on its own.
- Bootstrap trap: the cert comes from the DC, the DC is only reachable from the employee SSID, which needs the cert. `gpupdate` on guest Wi-Fi fails with "lack of network connectivity to a domain controller". Only exits: a wire (USB-C Ethernet dongle / dock / borrow a desktop's jack for 5 min), or a VPN whose tunnel is up before `gpupdate` runs. Do not export another laptop's machine cert — Computer-template keys are non-exportable, and the cert is that machine's identity (NPS maps SAN → computer account). Check `dsregcmd /status` first: `DomainJoined: NO` + `AzureAdJoined: YES` means Entra-only, which never auto-enrolls from the AD CA (needs Intune SCEP/PKCS or an AD join — different ticket).
- Cert present and still refused → NPS log on the RADIUS server: Security event 6273, Reason Code (16 bad creds, 22/23 cert/EAP chain or CRL, 48/65 not in allowed group). A batch of laptops dropping off the same month = CA/expiry problem, check other laptops' cert dates.

## Pitfalls
- `Resolve-DnsName ... -Server localhost` can time out while records are fine: `localhost` may go to `::1`, or the DC's first recursive lookup of an external CNAME target is slow. Retry with `-Server 127.0.0.1`, check the record alone with `-Type CNAME`, and test an external name (`microsoft.com`) to separate a forwarder/outbound-53 problem from a missing record. Confirm `hostname` too: the window may be the laptop, not the RDP session.
- AD-integrated zones replicate to the other DCs in minutes; no need to add the record on each DC — but a client may hit the other DC first (see step 4).
- Andrew pastes my blocks from Telegram into PowerShell: a `>>` prompt or a cmdlet prompting for a mandatory parameter means the paste lost quotes/lines - tell him Ctrl+C and retype the one line by hand. Fence one command per block, no `#` comments.
- Incident write-ups for work: issue -> cause chain -> fix -> "for next time" bullets, first person, plain. Leave out dead ends and attempted steps unless he asks; "make it sound human" = the de-AI pass in skill linkedin-writing.
